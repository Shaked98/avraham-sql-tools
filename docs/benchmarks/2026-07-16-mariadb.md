# MySQL 5.7 vs MariaDB 10.11 head-to-head — general workload + huge-text payloads

**Date:** 2026-07-16 · **Host:** i7-13700KF (24 threads, hybrid P/E cores), WSL2 (this run: ~23.5 GiB visible RAM — larger than the 15 GB cap of the two prior reports), consumer NVMe, Docker 29.4.3
**sql-replay:** 0.4.0, built `--release` from commit `5f442af` ("feat(sql-replay): first-class MariaDB targets with big-LONGTEXT fetch benchmark classes (#14)") — includes the MariaDB engine-family awareness, per-fingerprint result-byte stats, and size-decade regression gate, all exercised below
**Servers:** mysql:5.7 → **5.7.44**, mariadb:10.11 → **10.11.18-MariaDB-ubu2204** (official Docker images, run **sequentially, never simultaneous**, data on ext4 via Docker's default volume storage — never /mnt/c)

> One of four executed benchmark writeups behind the cross-engine table
> in the main [README](../../README.md#benchmarks-where-a-57-workload-regresses-on-80-vs-mariadb-1011).

Companion to [5.7 vs 8.0, general workload](2026-07-16-mysql80-general.md), [5.7 vs parity-pinned 8.0](2026-07-19-mysql80-parity.md) and [5.7 vs 8.0, huge-text payloads](2026-07-16-mysql80-hugetext.md): same rig shape, same class structure, so a cross-engine README table can be assembled from them.

## Verdict

1. **MariaDB 10.11 is a much safer 5.7 exit than 8.0 on this workload shape.** `compare` on the general workload: **zero regressions, zero improvements ≥ 20%, exit 0** — all 8 fingerprints within threshold, overall QPS **+7.6%** (93.3 → 100.5). Contrast with 8.0 on the same class structure: −60% QPS and a ~5x group-by loss.
2. **MariaDB does not share 8.0's join+GROUP BY pain — it's 15% *faster* than 5.7 on that class** (p95 340.5 → 288.8 ms, p50 −14%, charset pinned identically on both engines). The key open question from the prior reports is answered: the group-by cliff is an 8.0 phenomenon (TempTable engine + utf8mb4 defaults), not a "leaving 5.7" phenomenon. Point lookups, secondary-index lookups, inserts, and the 1 KB–254 KB LONGTEXT fetch classes are all within ±10% p95, sub-millisecond on both.
3. **Cross-engine result correctness is clean — new signal this run.** `--checksum` passes on both workloads: general 7 fingerprints checked / 6 matched / **0 MISMATCHED** / 1 advisory; blob 9 checked / 8 matched / **0 MISMATCHED** / 1 advisory (the advisory is `select @@version_comment` both times — a server-state read, correctly demoted). Even the join+GROUP BY class with `AVG(salary)` decimals aggregates to the **identical digest** on both engines (`f4816b2dcab2c29d`, 1,570 rows over 200 events), and the 15 MB documents drain to identical digests (`2dad93f1047f457b`, 377,487,360 bytes/pass). MySQL-5.7 text-protocol results and MariaDB-10.11 ones are byte-equivalent on this workload.
4. **Huge-text fetch is at par, with one honest wobble each way.** Full fetches of 100 KB–15 MB documents differ by single-digit percent in the mean at every concurrency; the only `compare`-flagged regression across all three levels is **full-fetch 1MB at C=12: p95 +23%** (6.4 → 7.9 ms, mean +18%). Single-stream 15 MB is slightly slower on MariaDB (mean +10%, ~912 → 833 MB/s). On the other side, MariaDB is consistently **faster at the server-side blob read** (`SUBSTRING(body,1,1024)` of 5 MB/15 MB docs at C=12: mean −19%/−31%) — same direction 8.0 showed, so this is a 5.7 weakness, not an engine quirk.
5. **The migration-relevant diff is behavioral, not performance: `sql_mode`.** The only settings diff `compare` found is MariaDB's default dropping `ONLY_FULL_GROUP_BY`, `NO_ZERO_IN_DATE`, `NO_ZERO_DATE` from 5.7's default. That's an honest engine-default difference (the new engine-family warning fired and said exactly that); queries that 5.7 rejects under ONLY_FULL_GROUP_BY would silently run on stock MariaDB. Pin `sql_mode` explicitly when migrating.

## Method

Same discipline as the two prior reports: sequential containers on port 13310, identical `my.cnf` mounted into both, dataset loads verified identical, capture from the live 5.7 workload, replay of the *same* captures against both engines with `--warmup --repeat 3` (median-aggregated), `--filter-user bench`, `--max-connections 24`, `--spool-dir` on real disk (/tmp is tmpfs here), then `compare` per pair. Memory guard checked before each leg (17–19 GiB available; budget never threatened).

**Everything pinned in `my.cnf`** (identical file both legs; every variable below exists on **both** engines — nothing was silently skipped; all verified applied via `SELECT @@...`, values identical including `log_bin=0`):

```ini
[mysqld]
innodb_buffer_pool_size = 4G          # verified 4294967296 on both
innodb_flush_log_at_trx_commit = 2
skip-log-bin
max_allowed_packet = 64M              # verified 67108864 on both
character_set_server = utf8mb4        # pinned on BOTH (MariaDB 10.6+ also defaults utf8mb4,
collation_server = utf8mb4_general_ci # but 8.0-style 0900 collations don't exist there; general_ci exists on both)
```

**Workloads** (both captured from live 5.7 under `long_query_time=0` slow log, dialect `mysql-5.7`):

- **General:** `verify/workload.sh` at current-main defaults — seed 42, **14 sessions** (the 5.7-vs-8.0 general run predates the two xml classes; its 4 core classes are unchanged): pk point lookups, hire-date secondary-index lookups, join+GROUP BY (~50k groups over ~470k joined rows), short audit INSERTs, plus xml LONGTEXT point/IN-list fetches spanning 1 KB–254 KB (five size decades — exercises the 0.4.0 byte stats). Employees dataset v1.0.7, canonical row counts verified on both; `idx_hire_date`, `verify_audit`, `verify_xmldoc` (300 rows, `SUM(LENGTH)`=18,342,660 — bit-identical both legs) as in the verify rig. 2,102 replayed events.
- **Blob:** mirror of the blob report — seeded (seed 42) byte-exact XML docs, 40×100KB / 20×1MB / 10×5MB / 4×15MB (~134 MB table, per-class `COUNT/MIN/MAX(LENGTH(body))` verified identical on both legs), full fetches (96/48/24/24 per pass) + `SUBSTRING(body,1,1024)` partial fetches (24/class), per-class column aliases to keep size classes as distinct fingerprints, at C ∈ {1, 4, 12} parallel sessions (289–300 events/capture).
- **Checksum passes:** one extra `--checksum` replay per leg of the general capture and of the blob C=4 capture (single pass; latencies of checksum runs only compared against other checksum runs, as the tool enforces).

## Result correctness (`--checksum`) — cross-engine, new this run

- **General pair:** 7 fingerprints checked, 6 matched, **0 MISMATCHED**, 1 advisory (`select @@version_comment limit ?` — digests differ because the engines *are* different servers: `204d62c2…` → `8f79be7e…`; correctly demoted as a server-state read). The INSERT class has no result sets, hence 7 checked of 8 matched fingerprints.
- **Blob C=4 pair:** 9 checked, 8 matched, **0 MISMATCHED**, 1 advisory (same fingerprint).
- Every deterministic class — including `AVG(s.salary)` decimal aggregation, DATE formatting in the hire class, and 15 MB LONGTEXT bodies — produced identical order-insensitive digests across engines. Digest evidence: gb `f4816b2dcab2c29d` (1,570 rows / 200 events) and full-fetch-15MB `2dad93f1047f457b` (377,487,360 result bytes/pass) on **both** engines.
- Checksum-pass latency compares (checksum runs vs checksum runs) exited 2 on sub-millisecond tails only: general-ck flagged one decade-confined item (IN-list fetch, 10KB–100KB decade, p95 0.31 → 0.48 ms, +53%) and blob-c4-ck flagged SUBSTRING-of-15MB/5MB p95 +64%/+54% with means +10%/+1% — classic scheduler-noise tails at 0.3–8 ms absolute, and the mirror image of the plain C=4 run where the same classes were flagged as *improvements*.

## Tool dogfood (sql-replay 0.4.0)

- **The MariaDB-targets feature (#14) worked end-to-end unmodified:** mysql-5.7-dialect captures replayed against 10.11 with 0 errors across ~13.5k executed events per leg; `server_family()` classified the candidate and the comparability warning framed the sql_mode diff correctly; the version slot shows `10.11.18-MariaDB-ubu2204`.
- **Byte stats + size decades (0.4.0) earned their keep:** the `res/query b→c` column proved both engines returned byte-identical result volumes per class, and the decade gate caught one decade-confined tail the top-level ranking correctly didn't flag. The blob report's 2026-07-16 recommendation ("surface result-set byte counts per fingerprint / size-aware bucketing") is now shipped and visibly working.
- **Memory model improvement vs the 0.2.0 blob run:** replay MaxRSS at C=12 on 15 MB rows is **324 MB** (5.7 leg) / **340 MB** (MariaDB leg) vs **650–720 MB** measured with 0.2.0 on the same workload shape — the post-M4 memtune work (buffer-pool cap + mallopt) roughly halved it. The visible cost: multi-MB fetch latencies are ~2x the 0.2.0-binary numbers (single-stream 15 MB p50 16.8 ms now vs 8.0 ms then; ~912 vs ~1780 MB/s), consistent with the documented page-fault tax of the 128 KiB buffer caps. Cross-run comparison is uncontrolled (different binary, different day) — but it means **absolute MB/s must not be compared across the blob report and this one**; within-run engine ratios are unaffected (both legs ran the same binary).
- Checksum passes cost ~nothing on this workload (general: 22.51s vs 22.52s wall; the drained bytes were already being read).
- Same sharp edge as the blob report: per-size-class fingerprints still require aliasing tricks (`AS body_c5m`); the decade split now mitigates the analysis side, but capture-side class identity still leans on SQL text.

## Exact commands

Scratch scripts in a throwaway `bench/` directory (leg.sh / gen_blob.py / analyze.py; kept out of the repo — no project source modified). The meat:

```sh
cargo build --release   # commit 5f442af, sql-replay 0.4.0
# identical my.cnf (above) mounted at /etc/mysql/conf.d/zz-bench.cnf; sequentially:
docker run -d --name sqlt-maria-bench -p 127.0.0.1:13310:3306 -e MYSQL_ALLOW_EMPTY_PASSWORD=yes \
  -v bench/my.cnf:...:ro -v bench/test_db:/test_db:ro mysql:5.7
#   (MariaDB leg: mariadb:10.11 with MARIADB_ALLOW_EMPTY_ROOT_PASSWORD=yes)
# per leg: load employees v1.0.7 (row counts asserted); idx_hire_date + verify_audit +
#   verify_xmldoc (SUM(LENGTH) asserted identical); docsdb + 134MB seeded docs.sql
#   (per-class LENGTH asserted identical); 5.7 only: 'bench' user, slow log per phase,
#   verify/workload.sh all (seed 42, 14 sessions) + C∈{1,4,12} parallel blob sessions
target/release/sql-replay capture --input <phase>.log --out captures/<phase>.jsonl.zst
/usr/bin/time -v target/release/sql-replay replay --capture captures/<phase>.jsonl.zst \
  --url mysql://root@127.0.0.1:13310/<db> --db-override <db> --filter-user bench \
  --max-connections 24 --spool-dir bench/spool --warmup --repeat 3 \
  [--allow-writes]  --out runs/run-{57,maria}-<phase>.json     # + one --checksum pass each
target/release/sql-replay compare --baseline runs/run-57-<p>.json \
  --candidate runs/run-maria-<p>.json --top 20 --json ... --out ...html
# exits: general 0 · blob-c1 0 · blob-c4 0 · blob-c12 2 (1MB class) · ck-pairs 2 (sub-ms tails)
docker rm -f sqlt-maria-bench   # verified: no bench containers left after either leg
```

## Caveats

- **WSL2 virtualization, hybrid P/E cores, loopback docker-proxy, shared box (other workloads resident but quiet): ratios between engines measured back-to-back are the output; absolute numbers are not production predictions.** This box also had more RAM visible than the prior reports' 15 GB cap (~23.5 GiB) — another reason not to compare absolute numbers across reports.
- **This run pins utf8mb4 on both legs** (by design) — its 5.7 baseline is therefore slower on the gb class than the general 5.7-vs-8.0 report's stock-latin1 5.7. Any cross-report table should label the baselines (latin1-5.7 vs utf8mb4-5.7).
- Sub-millisecond classes remain scheduler-noise territory; the checksum-pair exit-2s and the ±30–50% SUBSTRING p95 swings (flagged as improvements at C=4, mixed at C=12) should be read as "par, noisy tails", with means the stabler column. p95 on 24-sample classes is effectively 2nd-worst-of-24.
- Single seeded workload (seed 42), one dataset each, 14/12 sessions max — one workload shape, not a general MariaDB verdict. Write coverage is one short-INSERT class; no UPDATE/DELETE/DDL/transaction-shape coverage.
- MariaDB ran without io_uring (WSL2 disables it) — an I/O-bound workload might shift on real hardware; this one was fully buffer-pool-cached after warmup by design.
- MariaDB's `@@version_comment` digests differing is expected; all correctness claims are about the 14 deterministic workload fingerprints (of 16 checked).
- Same `verify_audit` start-state asymmetry as the prior runs (capture-side table had live-workload rows before replay); negligible at this size.

## Recommendations

1. **For the migration question:** on this evidence, evaluate MariaDB 10.11 as the primary 5.7 exit path — it removes the one big 8.0 loss (group-by/temp-table classes) instead of inheriting it, matches 8.0's blob-read improvement over 5.7, and returned bit-identical results on every deterministic class. The two things to actually engineer around are behavioral: pin `sql_mode` explicitly (ONLY_FULL_GROUP_BY absent by default) and pin charset/collation (no 0900 collations exist; `utf8mb4_general_ci` is the portable choice).
2. **Watch items to re-measure on real hardware:** 1MB-class fetch tail under high concurrency (+23% p95 at C=12) and single-stream ≥5MB transfer (+5–10% mean) — both small, both plausibly WSL2-flavored, both the kind of thing this tool's compare gate re-checks cheaply.
3. **For the cross-engine README table** (now in the main [README](../../README.md#benchmarks-where-a-57-workload-regresses-on-80-vs-mariadb-1011)): use the general-workload table's four classic classes + gb, and the blob C=1/C=12 full-fetch rows; take 8.0 columns from the two prior reports with a footnote that the 8.0 general run was stock-charset (confounded by design) while this run is charset-pinned, and that blob MB/s absolutes are not comparable across tool versions (0.2.0 vs 0.4.0 memory model).
4. **Tool (minor):** nothing broke; the one enhancement this run suggests is letting `compare` annotate checksum-run latency sections more loudly as "checksum-plane latencies" so a reader doesn't mistake the ck-pair exit 2 for a plain-run regression.
